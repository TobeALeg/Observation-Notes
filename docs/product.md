# Product —— 创业判断日志

## Production

### 用户是谁
正在早期公司 / AI 咨询公司里工作的未来创业者。现在没有足够资源独立创业，但每天都在真实商业现场旁观 founder 如何判断、如何下注、如何混淆验证、如何犯错或做对。

### 核心价值
把和 AI 的对话沉淀成一组真实 Case：同一个公司问题上，老板怎么判断，我怎么判断，分歧来自哪里，最终现实如何裁判。长期目标是训练自己的创业判断系统，而不是证明老板错。

### 产品原则
1. **Case 不是一次对话**：Case 是一个可被现实验证的判断问题。一次复杂对话可以拆出多个 Case，一个 Case 也可以被多次对话补充。
2. **分歧优先**：每个 Case 必须写清老板判断、我的判断、分歧本质，而不是只记录情绪或结论。
3. **现实校准**：状态不是任务进度，而是现实反馈：待验证 / 我更接近 / 老板更接近 / 双方都错 / 混合结果 / 无解。
4. **无解也要解释**：商业里很多事不是谁对谁错。无解时必须说明原因：样本太小、条件变化、目标不一致、执行不完整或信号太弱。
5. **未来创业提醒是最终沉淀**：每个 Case 最终要回答“如果未来我是 founder，这件事提醒我什么？”
6. **概念服务 Case**：business / marketing 概念可以记录，但只放在 `docs/business-concepts.md` 作为辅助词典，不做知识网络。

### 不做什么
- 不做 Obsidian 式双链知识库。
- 不把“知识点”作为一级产品对象经营。
- 不记录所有聊天，只记录能形成判断训练价值的内容。
- 不做账号、多用户、云同步、App 内 LLM。
- 不把复盘做成任务管理看板。

### 用户体验路径
1. 用户发来一段复杂对话或工作现场。
2. AI 先做拆分：候选 Case / Signal / Concept / Reflection。
3. 用户确认这次要记录哪些 Case。
4. AI 写入 `data/cases/*.md`，必要概念补到 `docs/business-concepts.md`。
5. 用户在 GitHub Pages 查看 Case、复盘队列、判断主线和原则。
6. 现实出现反馈后，用户在对话里告诉 AI，由 AI 回填结果、状态、为何无解和未来创业提醒，再发布新快照。
7. 多个 Case 反复验证后，再提炼到 `data/principles/*.md`。

## UX

### 设计原则如何回应以上要求
- **Cases 为默认视图**：主问题是“我正在追踪哪些判断分歧”，不是“我最近记了什么”。
- **Review 是现实校准**：按状态扫描判断结果，但不做三列任务看板，避免把产品拖向项目管理。
- **Principles 高门槛**：只有从多个 Case 中反复出现的模式，才沉淀成未来创业原则。
- **Glossary 辅助化**：概念解释保留，但不做详情页、分类页、互链图谱。
- **网页只负责阅读与复盘**：GitHub Pages 不具备服务端写入能力；新建、定稿和回填都回到对话与 Git，避免出现无法真实保存的假编辑器。
